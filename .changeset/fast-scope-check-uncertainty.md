**`/gsd-fast` no longer bounces mechanical work to `/gsd-quick` on file count, and its commit stages only the files it touched.** The `scope_check` step gated the fast lane on "≤ 3 file edits, ≤ 1 minute of work" — a proxy that fails on exactly the work the lane exists for: deleting a component along with its spec and its styles touches four or five files and requires no planning at all. The bounce is not free either; the user has already paid a full turn loading the workflow and the project's CLAUDE.md, gets nothing back, and then pays the entire `/gsd-quick` pipeline — planner, executor, code-reviewer, three fresh contexts — on top, which is strictly worse than if `/gsd-fast` had never existed. The gate now tests real uncertainty instead of size: bounce only when you would have to research first, when the intent is ambiguous enough that you would be guessing, when the change adds a dependency, a new architectural pattern, or a schema/API contract change, or when it spans more than ~10 files or must be sequenced across several commits — and never on file count, line count, or a vague sense that the change is "big". Deletions, renames, dead-code cleanup, config changes, and mechanical edits repeated across a handful of files are now explicitly in scope, and `<success_criteria>` measures what the lane actually guarantees (no subagents, no PLAN.md) rather than wall-clock minutes. Separately, the `commit` step ran `git add -A`, sweeping any unrelated change the user happened to have in flight into the task's commit and breaking the atomic-commit guarantee the same workflow declares two sections lower; it now records the working tree's pre-existing dirty paths before doing the work, stages only the paths it actually created, edited, or deleted, and prints the staged set so a foreign path can be unstaged before the commit lands.
